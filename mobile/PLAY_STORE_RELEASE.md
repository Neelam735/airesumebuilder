# Play Store Release Guide — Resume Forge AI

A step-by-step checklist to take the app from a local `flutter run` to a
signed, production release on Google Play, **including** getting the
`Pay with Google Play` flow to actually work.

> Why "Pay with Google Play" fails today: Google Play Billing **cannot** work on
> a raw `flutter run` debug build. The in-app product must exist and be
> **active** in Play Console, the app (with that product) must be uploaded to a
> **testing track**, the build must be **signed with your upload key**, and your
> Google account must be a **licensed tester**. Steps 3–7 below fix this.

---

## 0. One-time identity decisions

Pick these once and keep them consistent everywhere:

| Thing | Example | Notes |
|------|---------|-------|
| `applicationId` | `com.neelam.resumebuilder` | Must be globally unique on Play. Cannot change after first upload. |
| App name | `Resume Forge AI` | Shown on the device + listing. |
| In-app product ID | `ai_resume_improvement` | Must match `BillingService.productId`. |
| Backend URL | `https://your-app.up.railway.app` | Your deployed HTTPS backend. |

If you change the `applicationId`, update it in `android/app/build.gradle`
(`namespace` + `applicationId`) and re-create the Play Console app.

---

## 1. Deploy the backend (required before release)

The app is useless on real phones until the backend is reachable over HTTPS.
Deploy `backend/` to Railway (free subdomain, no domain purchase needed):

1. Railway → New Project → Deploy from GitHub → this repo → root dir `backend/`
   (or use the `backend` branch). It auto-detects the `Dockerfile`.
2. Set env vars: `GEMINI_API_KEY`, `GEMINI_MODEL=gemini-2.5-flash`,
   `PAYMENT_TOKEN_SIGNING_KEY` (long random string),
   `GOOGLE_PLAY_PACKAGE_NAME=com.neelam.resumebuilder`,
   `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` (see step 6).
3. Settings → Networking → Generate Domain.
4. Verify: `https://your-app.up.railway.app/api/v1/health` → `{"status":"UP"}`.

## 2. App signing (upload key)

Google requires a signed release build. Generate an upload keystore **once**:

```bash
cd mobile
bash scripts/setup-keystore.sh
```

This creates `android/keystore/upload-keystore.jks` and `android/key.properties`
(both git-ignored). **Back up the keystore offline** — losing it means you can
never update the app again.

Then merge the signing config into `android/app/build.gradle`. Open
`android/signing.gradle.example` and apply it — the key parts:

```gradle
// top of the file, after the other imports
def keystoreProperties = new Properties()
def keystorePropertiesFile = rootProject.file('key.properties')
if (keystorePropertiesFile.exists()) {
    keystoreProperties.load(new FileInputStream(keystorePropertiesFile))
}

android {
    // ...
    signingConfigs {
        release {
            keyAlias keystoreProperties['keyAlias']
            keyPassword keystoreProperties['keyPassword']
            storeFile keystoreProperties['storeFile'] ? file(keystoreProperties['storeFile']) : null
            storePassword keystoreProperties['storePassword']
        }
    }
    buildTypes {
        release {
            signingConfig signingConfigs.release
            minifyEnabled true
            shrinkResources true
            proguardFiles getDefaultProguardFile('proguard-android-optimize.txt'), 'proguard-rules.pro'
        }
    }
}
```

> Note: `android/app/build.gradle` is generated by `flutter create` on your
> machine, so it isn't tracked in this repo — edit your local copy.

## 3. Cleartext / network security (production hardening)

For local dev we set `android:usesCleartextTraffic="true"` in
`android/app/src/main/AndroidManifest.xml` so `http://10.0.2.2:8080` works.

For a **production** build talking to an **HTTPS** backend you should NOT ship
cleartext-allowed. Two options:

- **Simplest:** before building the release AAB, remove
  `android:usesCleartextTraffic="true"` from the `<application>` tag (your
  backend is HTTPS, so it isn't needed).
- **Keep dev working too:** delete that attribute from the main manifest and add
  a debug-only override at `android/app/src/debug/AndroidManifest.xml`:

  ```xml
  <manifest xmlns:android="http://schemas.android.com/apk/res/android">
      <application android:usesCleartextTraffic="true" />
  </manifest>
  ```

## 4. Build the release bundle (AAB)

Point the build at your production backend and product id via `--dart-define`:

```bash
cd mobile
flutter clean
flutter pub get
flutter build appbundle --release \
  --dart-define=API_BASE=https://your-app.up.railway.app \
  --dart-define=GOOGLE_PLAY_PRODUCT_ID=ai_resume_improvement
```

Output: `build/app/outputs/bundle/release/app-release.aab`.

Bump `version:` in `pubspec.yaml` (e.g. `1.0.0+1` → `1.0.1+2`) for every new
upload — Play rejects duplicate version codes.

---

## 5. Create the app + upload in Play Console

1. [Play Console](https://play.google.com/console) → Create app.
2. Fill the mandatory listing bits (name, short/full description, icon,
   feature graphic, screenshots, category, contact email, **Privacy Policy
   URL**).
3. Complete: Content rating, Target audience, Data safety, Ads declaration.
4. Testing → **Internal testing** → Create new release → upload
   `app-release.aab` → roll out.
5. On the Internal testing track, add your Google account under **Testers**.

> Play now uses **Play App Signing**: they re-sign with a Google-managed app
> key; your upload key just proves it's you. That's fine and expected.

---

## 6. Backend ↔ Play verification (service account)

The backend verifies purchases via the Google Play Developer API, so it needs a
service account:

1. Play Console → Setup → **API access** → link a Google Cloud project.
2. Create a **service account** in Google Cloud, download its JSON key.
3. Back in Play Console → API access → grant that service account access with
   at least **View financial data / Manage orders** for this app.
4. Put the JSON into the backend env var `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON`
   (inline JSON or a file path) and set `GOOGLE_PLAY_PACKAGE_NAME` to your
   `applicationId`. Redeploy the backend.

---

## 7. Create the in-app product (fixes the "not available" error)

1. Play Console → Monetize → **Products → In-app products** → Create product.
2. **Product ID:** `ai_resume_improvement` (must match exactly — it is
   case-sensitive and cannot be reused once created).
3. Set a name, description, and price (e.g. ₹29). **Activate** it.
4. Wait for it to show **Active**. New products can take a few hours to
   propagate to devices.

Then test on a **real device**:

- Sign in on the phone with the **licensed tester** Google account.
- Install the app **from the Internal testing link** (or `flutter install
  --release` of the *same* signed build whose `applicationId`/version was
  uploaded). Billing checks the installed signature against Play.
- Open the app → Enhance → Download → **Pay with Google Play**. You'll get a
  test purchase dialog (testers are not charged).

If it still says *not available*, the app now shows the precise reason
(`billing not available` vs `product not found`). Checklist:
- Product is **Active** (not draft) and IDs match exactly.
- The build is **signed** and uploaded to a track; you installed *that* build.
- Your account is a **licensed tester** and the track includes your account.
- Give it time — activation/propagation can lag by a few hours.

---

## 8. Final pre-launch checklist

- [ ] Backend live on HTTPS; `/api/v1/health` returns `UP`.
- [ ] `applicationId` final and consistent (app, product package name, backend).
- [ ] Release build signed with your upload key.
- [ ] `usesCleartextTraffic` removed (or debug-only) for the release build.
- [ ] `--dart-define=API_BASE=<https prod url>` used for the release build.
- [ ] In-app product **Active**, ID matches `ai_resume_improvement`.
- [ ] Service account wired to the backend; test purchase verified end-to-end.
- [ ] Privacy Policy URL, Data safety, Content rating completed.
- [ ] Screenshots, icon, feature graphic uploaded.
- [ ] Version code bumped.

Promote from Internal testing → Closed/Open testing → Production when ready.
